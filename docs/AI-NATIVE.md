# AI-native 设计说明：为什么是锚点，不是摘要

## 一、一个具体的痛点

**长视频学习的真实成本不在"看完"，而在"回到那一秒"。**

任何一个真的用视频学习的人都有过这个动作：记得某个教授讲过一个绝妙的例子，想引用、想重看、想记下来——然后花十分钟拖进度条，最后放弃，改用别人的二手总结。这个过程里有三笔可测量的成本：

| 成本 | 具体表现 | 现有产品的处理 |
| --- | --- | --- |
| **定位** | 记得"有个例子"，但不知道在第几分钟 | 摘要类产品把视频压成文字，**恰好销毁了唯一可用于回溯的坐标（时间）** |
| **验证** | 摘要说得头头是道，但无法确认是不是原话，更无法确认是不是讲师的观点还是模型的推断 | 不标注出处，或标注一个笼统的"视频中提到" |
| **等待** | 两小时的视频分析要几十秒到几分钟，这段时间产品完全不可用 | 转圈 + "正在分析…" |

第三笔成本最容易被忽视，但它是产品体感的全部：**等待不是加载，等待是产品的一部分**。如果一个工具的产出要等 40 秒，用户在这 40 秒里的心智已经从"我要学这个"滑到"算了我先干别的"。

于是有了本项目的主张：**AI 不该把长视频变得更短，应该把长视频变得可寻址。**

## 二、由这个痛点推出的五个选择

下面每一条都是"AI-native 才会这么做"，而不是"把模型接上去"。

### 1. 产出物是坐标网络，不是文本

常规做法：一段摘要 + 几个 bullet。问题在于摘要是一次性的消费物，读完即弃，且不可执行。
本项目的产出物是 `Anchor`——`start` / `end` / `quote` / `why` / `confidence` / `dependsOn`。它本身不是内容，而是一个**可执行的对象**：点一下就回到那一秒；`dependsOn` 让"先看 12:30 再看 18:40"成为一条真实的路径。
代码：`lib/types.ts`、`components/video/anchor-graph.tsx`

### 2. 验证优先于生成

常规做法：让模型自由发挥，输出什么就渲染什么。
这里的约束是三道：zod schema 限定字段与取值 → 模型给出的 `quote` **必须能在字幕里逐字找到**，找不到就整条丢弃（`quoteExists`）→ 时间戳由代码从事件区间推算，模型无权发明时间。
由此得到的取舍是：**宁可少给，不可给假**。一个只有 4 个锚点的视频，比 12 个里 5 个是编的更有用。
代码：`lib/schema.ts`、`lib/analyze.ts`

### 3. 检索优先于长上下文

常规做法：把整份字幕塞进 prompt，让模型自己找。
这在两小时的课上既贵又不可靠，而且**无法回答"你凭什么这么说"**。本项目先把字幕切成语义事件（静默间隔 + 话语标记 + 词汇漂移），检索时用 BM25-lite 在事件级打分，命中低于阈值就**确定性地拒答**，并给出最近的邻近内容——拒答是产品行为，不是失败。
代码：`lib/segment.ts`、`lib/retrieval.ts`、`app/api/chat/route.ts`

### 4. 交付是渐进的

常规做法：一个请求、一个响应、一个 spinner。
这里 `/api/analyze/stream` 用 SSE，把"读取字幕 → 切分事件 → 标注锚点 → 串联依赖"四个阶段逐个下发，**每验证通过一个锚点就立刻推给前端**。用户可以在前十钟已经可读时，后九十分钟仍在跑。播放器一进页面就挂载，不等分析完成。
代码：`app/api/analyze/stream/route.ts`、`app/video/video-page-content.tsx`

### 5. 不确定性必须可见

常规做法：把置信度藏起来，让输出看起来都一样确定。
这里 `confidence` 直接印在卡片上（低于 0.5 会标 `low`），`source` 明确区分 `live` / `heuristic`（有字幕没模型）/ `demo`（无字幕时的示例），降级时 `notice` 如实说明。**一个你无法验证的高置信结论，比一个可验证的低置信指针更糟。**
代码：`components/video/anchor-list.tsx`、`lib/analyze.ts`

## 三、与当前前沿的对接与取舍

- **事件级检索（Event Chain RAG 的思路）**：把"帧级 / 片段级"的检索单位提到"语义事件"，再在事件内做时刻标注。这解释了为什么本项目坚持自己分段，而不是按固定 60 秒切块——固定的块会把一个论点和它的反例切到两个块里，而检索恰恰需要它们在一起。
- **原生视频理解的时间戳能力**：现在的主流多模态模型已经能直接吃视频并要求它引用 `MM:SS`。本项目的做法是**让代码而不是模型承担时间戳的权威性**：模型说"大约在 18 分钟"，代码只接受落在已知事件区间内的时刻。这比相信模型的时间算术更稳。
- **2026 年 AI 产品 UX 的共识**：流式是默认、过程透明、错误可恢复、诚实展示不确定性。上面第 4、5 条就是它的落地，而不是照抄一句原则。
- **取舍**：本仓库**没有新增任何依赖**（`pnpm-lock.yaml` 失效会让 Vercel 部署直接失败）。因此模型走 OpenAI 兼容的 `/chat/completions`，缓存走 Upstash REST，字幕自己解析。代价是放弃了 vendor SDK 的多模态便利，收益是可以在任何兼容端点上跑。

## 四、还没做到的（诚实清单）

1. **视觉通道没读**。锚点上的 `visual` 字段是模型对上下文猜的，不是证据。下一步应该是按锚点区间抽帧，把画面文字/图表作为第二证据源合流。
2. **只有英文学术话语标记**（`so`、`the key is`、`however`…）。中文等语言目前退化到静默切分，这会让"论点 / 反例"的边界变粗。
3. **没有评测集**。"锚点好不好"目前靠人眼判断。要做的是拿 20 个已知有金标时刻的讲座，量 `recall@k` 和"引用可验证率"——这是把产品从 demo 变成工具的分界线。
4. **缓存与限流是单实例的**。内存 LRU + 进程内计数只是刹车，不是配额系统。上多实例要换共享存储，并加真正的鉴权。
5. **成本与采样策略**：目前对每个事件都调用一次模型。两小时 40 个事件就是 40 次调用，应该先对事件做一次廉价筛（信息密度/转折词），只对高分事件精细标注。

## 五、一句话

> 摘要把视频变成你可以读完的东西，锚点把它变成你可以回去的东西。
> AI-native 不是"用模型生成内容"，是**用模型重建一个本来不存在的可寻址结构**，并且让每一处都经得起回看。
